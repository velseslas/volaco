# Audit complet de la plateforme vs Cahier des Charges V7.0

**Date :** 24 octobre 2026  
**Périmètre :** `apps/api`, `apps/studio`, `packages/core`, routes, stores, tests, runtime local  
**Source de vérité :** Cahier des Charges Final V7.0 (sections 9 à 63), matrice V7-WIRING, audits existants, code réel  
**Nature :** audit de couverture et de branchement, pas une certification de conformité

---

## 1. Verdict exécutif

La plateforme **n'est pas à 100 % du CDC V7.0**. C'est un monolithe modulaire avancé, avec un cœur IA réellement branché et testé, mais les couches « plateforme » du CDC (données, déploiement, collaboration, billing, production, distribué, DR, conformité) sont absentes ou très partielles.

| Indicateur | Résultat |
|---|---:|
| Modules CDC 9-31 (cœur produit) | **≈ 54 %** de couverture moyenne |
| Modules CDC 32-51 (plateforme / Enterprise) | **≈ 20 %** de couverture moyenne |
| Global 9-51, pondération égale | **≈ 38 %** |
| Modules avec un branchement réel | **19 / 43** (dont 4 avec réserves majeures) |
| Modules partiels | **15 / 43** |
| Modules absents | **9 / 43** |
| Modules ≥ 75 % | **1 / 43** (Application Audit) |
| Modules 60-74 % | **8 / 43** |
| Modules 40-59 % | **16 / 43** |
| Modules < 40 % | **18 / 43** |

**Lecture :** « branché » ne signifie pas « conforme au CDC ». Un module peut être branché dans le flux produit et ne couvrir que 40-55 % de ses exigences. C'est le cas de l'Application Model, de la DNA, du Plan Engine, de l'Impact Intelligence et de l'Agent Architecture.

---

## 2. Méthode et barème

### 2.1 Critère de branchement

Un module est considéré **BRANCHÉ** lorsque les cinq conditions sont réunies :

1. service réellement instancié ;
2. utilisé par un flux produit réel (route, stream, Studio) ;
3. persistance ou trace ;
4. test automatisé ;
5. preuve live ou preuve d'exécution documentée.

Si une condition manque, le module est **PARTIEL**. S'il n'y a pas d'implémentation, il est **ABSENT**.

### 2.2 Barème de couverture

Le pourcentage est une **estimation de couverture fonctionnelle et technique** des exigences du module, arrondie à 5 points. Il ne mesure pas la qualité du code ni la dette. Fourchette d'incertitude : ±10 points.

- **75-100 %** : exigences principales couvertes, branchement réel, quelques sous-exigences manquantes.
- **50-74 %** : service et flux réels, mais sous-exigences structurantes absentes.
- **25-49 %** : service ou route présente, mais non branché par défaut ou trop incomplet.
- **0-24 %** : squelette, maquette, ou absence.

### 2.3 Statuts

| Statut | Signification |
|---|---|
| `BRANCHÉ` | service + flux + persistance + test + preuve |
| `BRANCHÉ*` | branché, mais réserve majeure sur la couverture CDC ou le chemin par défaut |
| `PARTIEL` | service/route/UI existants, mais flux incomplet ou sous-exigences majeures absentes |
| `ABSENT` | pas d'implémentation réelle |
| `N/A` | section de gestion, de principes ou de documentation, non évaluable comme module logiciel |

## 6. Ce qui est réellement branché

### 6.1 Flux conversationnel `/stream`

Le flux principal est un **stream SSE hybride** :

- classification d'intention ;
- plan déterministe ;
- impact analysis avant mutation ;
- décision consultative ;
- préflight d'ingénierie ;
- génération provider ;
- parsing de sections ;
- mutation orchestrée avec vérification et rollback ;
- persistance fichier + révision ;
- Quality Gate visuel ;
- validation consultative ;
- événements et `done` enrichis.

Ce flux est réel et testé, mais il n'est pas le pipeline canonique complet `ConversationIntelligenceService → agent-runtime → MutationOrchestrator` pour la génération. La préparation unifiée existe derrière `VOLACO_UNIFIED_PIPELINE`, désactivé par défaut. C'est une dette d'architecture assumée.

### 6.2 Application Model, DNA, mémoire

- Application Model : reconstruit depuis les sources réelles, upsert après mutation, panneau Studio.
- DNA/Understanding : extraction stack/architecture/composants, lecture Studio, utilisation dans le modèle et l'impact.
- Mémoire projet : sessions durables, mémoire conversationnelle, signaux de décision, contraintes/risques.

### 6.3 Visual, Design Harmony, Audit, Feature Intelligence

- Visual Intelligence : rendu Chromium réel, DOM normalisé, critique déterministe.
- Design Harmony : tokens, drift, composants, cross-page, responsive/a11y, score AQS, recommandations.
- Application Audit : 8 auditeurs, findings, score, remédiation partielle.
- Feature Intelligence : découvertes, graphe, cycle de vie, panneau Studio.
- Evolution produit AINT-017 : readiness, santé, propositions, panneau Studio.

### 6.4 AI Orchestrator, sandbox, apply

- `/orchestrate` : plan multi-agents, preview dry-run, apply confirmé.
- Sandbox navigateur : Chromium headless, réseau coupé, tests fonctionnels DOM, verdict avant écriture.
- Rollback et audits de mutation.
- Limite : isolation processus, pas conteneur/OS complet.

### 6.5 Sécurité applicative et exploitation

- Auth JWT HMAC-SHA256, scrypt, `timingSafeEqual`.
- RBAC OWNER/ADMIN/ENGINEER/VIEWER.
- Rate limiting, secure headers, audit logs, masquage des secrets.
- Production : auth stricte si `VOLACO_API_KEY` configurée.
- FinOps, GDPR export/erase, observabilité, health.

## 9. Sécurité : points forts et risques résiduels

### Points forts

- Mots de passe scrypt + sel, comparaison `timingSafeEqual`.
- JWT signé HMAC-SHA256, secret d'auth.
- RBAC et permissions par route.
- Rate limiting et en-têtes de sécurité.
- Audit logs avec sanitisation des secrets.
- Sandbox réseau coupé, permissions refusées, V8 heap borné.
- Capability boundaries et permissions d'outils.
- Image gate fail-closed.

### Risques résiduels

1. **Clé Mistral dans le navigateur.** Le Studio stocke `vibecode_mistral_key` dans `localStorage` et l'envoie via `X-Mistral-Api-Key` ; la route `/stream` accepte cet en-tête. Si l'exigence est « clé uniquement côté serveur », ce point n'est pas conforme.
2. **Clés provider en clair.** `ai-provider-keys.json` est un JSON non chiffré dans `.volaco-data`. Pas de KMS/secrets manager, pas de chiffrement au repos démontré.
3. **Pas de garde prompt injection runtime.** Le masquage et l'audit existent, mais pas de policy engine d'entrée/sortie, ni de filtrage systématique des appels d'outils.
4. **Pas de RLS PostgreSQL.** L'isolation tenant est applicative ; une migration DB devra ajouter RLS.
5. **Pas de WAF/TLS/DDoS applicatif.** Ces exigences dépendent d'une infrastructure absente.
6. **Pas de backup/DR.** Les données SQLite/fichiers ne sont pas couvertes par PITR ou réplication.
7. **Pas d'OpenAPI/security schemes.** L'écosystème API n'est pas formalisé.

1. **Preuve provider réelle et fallback.** Redémarrer l'instance avec le build courant, prouver `/stream` Gemini ou Mistral, et garantir un fallback propre sur 401/404 sans exposer la clé.
2. **Data platform.** PostgreSQL + RLS + JSONB + pgvector + Redis + Object Storage ; migrer les stores SQLite/JSON.
3. **Deployment.** Staging/production, domaines, HTTPS, variables/secrets, historique, health checks, rollback, multi-provider.
4. **Sécurité Enterprise.** Secrets manager, chiffrement au repos, WAF/TLS/DDoS, suppression de la clé Mistral du navigateur, garde prompt injection.
5. **Collaboration.** Yjs/CRDT, présence, cursors, commentaires, branches/commits/reviews.
6. **Production Intelligence.** Monitoring, détection, diagnostic, recommandation, auto-repair post-déploiement.
7. **Billing & Credit.** Plans, abonnements, usage IA/compute/storage, RESERVE/CONFIRM/RELEASE, alertes FinOps.
8. **DNA Evolution.** Versioning, diff, rollback, branching, merging, provenance du DNA.
9. **API & Ecosystem.** OpenAPI 3.1, OAuth2, API keys/scopes, webhooks, idempotency, pagination, SDK/CLI.
10. **Observability/SRE/DR et conformité.** OTel/Prometheus/Grafana, SLO, PITR, backups, i18n, GDPR complet, IP/trust.

## 12. Conclusion

La plateforme possède un **cœur IA réellement branché** : conversation SSE, intention, plan, impact, décision consultative, validation, mutation orchestrée, Quality Gate visuel, audits, Design Harmony, Feature Intelligence, sandbox et apply confirmé. Ce n'est pas une maquette.

Mais le CDC V7.0 est plus large que ce cœur. Les couches **données, déploiement, collaboration, billing, production, distribué, DR, scale, i18n et conformité** sont absentes ou très partielles. La couverture globale est d'environ **38 %** en pondération égale, avec **54 %** sur le cœur produit et **20 %** sur la plateforme/Enterprise.

**À retenir :** les lots WIRE/PREP/LOT ont réellement branché des moteurs, mais ils ne constituent pas une conformité CDC complète. Le prochain saut de maturité n'est pas un nouveau moteur IA ; c'est la **plateforme autour du moteur** : données, déploiement, sécurité d'exploitation, observabilité et commercialisation.
