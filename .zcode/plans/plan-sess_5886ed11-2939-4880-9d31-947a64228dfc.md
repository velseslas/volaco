# ORDRE D'EXÉCUTION — « rien ne casse » : chaque étape est gardée par la suite de tests (1067+ verts)

## Pourquoi CET ordre (le raisonnement qui prime)

Le principe : **on ne construit jamais sur du fragile**. Donc : (1) on blinde d'abord ce qui protège tout le reste et qui ne peut rien casser ; (2) on restructure ce qui serait à refaire plus tard (le routeur) AVANT d'ajouter de nouvelles routes ; (3) on swappe la persistance SANS toucher aux interfaces (routes/UI inchangées) ; (4) l'auth vient après la base de données (elle a besoin d'une table users) mais avant tout ce qui est multi-utilisateur ; (5) les fonctionnalités à risque de régression (fichiers sur disque, boucle auto) viennent en dernier, sur une base durcie ; (6) le Design Intelligence (la vraie valeur V8) en finissant, car il se construit sur DNA + Quality Gate + rendu réel — tous désormais vivants.

## ÉTAPE 1 — Blindage zéro-risque (protège tout ce qui suit)
1. **Anti-fuite de secrets local** : script `scripts/check-secrets.mjs` (scanne mstrl_/sk-/AIza/ghp_…) branché en `pre-commit` via hook git + `npm run security:check` — zéro dépendance, marche sans CI.
2. **En-têtes de sécurité** (Annexe F) : `X-Content-Type-Options: nosniff`, `Referrer-Policy`, `Permissions-Policy`, `X-Frame-Options: SAMEORIGIN` (sauf routes de preview), CSP adaptée au Studio. HSTS réservé au jour où on sert en HTTPS. Non cassant : en-têtes additifs seulement.
3. **Unifier les tests** : supprimer vitest (devDep + config) au profit de node:test (déjà le runner de `npm test`) — la suite qui protège chaque étape suivante doit être unique et fiable.

## ÉTAPE 2 — Refactor du dispatcher de `server.ts` en mini-routeur
Table de routes déclarative (`méthode + motif → handler`) remplaçant la chaîne if-return. **Pourquoi maintenant** : toutes les étapes suivantes (auth, DNA, décisions…) ajoutent des routes — les faire sur le nouveau routeur évite de tout recâbler deux fois. Fait au moment où seuls MES lots récents existent = surface de régression minimale. Suite verte obligatoire.

## ÉTAPE 3 — Persistance SQLite derrière les interfaces existantes
`node:sqlite` est intégré à Node 24 (vérif au démarrage de l'étape ; plan B : better-sqlite3, plan C : JSON durci + sessions persistées). Swap **sans changer une seule route ni le front** :
1. `projects` → SQLite, puis `revisions`, `activity`, `audit`, `usage` (coûts IA enfin durables).
2. **Sessions de conversation persistées** → la classe de bugs « session morte après redémarrage » disparaît définitivement (l'auto-réparation devient un filet, plus une béquille).
Chaque store migré = commit + suite verte ; rollback trivial par store.

## ÉTAPE 4 — Authentification réelle (dépend de l'étape 3)
1. Table `users` (hash scrypt intégré à Node), endpoints `POST /auth/signup`, `/auth/login` → **JWT signé HMAC** (AUTH_SECRET, déjà prévu dans `.env.example`), tenant créé par utilisateur.
2. `extractRequestContext` : JWT valide → contexte (tenantId = tenant de l'utilisateur, rôle du token) ; la clé Bearer admin et le fallback headers dev sont **conservés** pour ne rien casser localement.
3. Studio : mini écran de connexion, token en localStorage, header Authorization centralisé dans `studioApiHeaders()`.
4. Tests cross-tenant (CDC §37) : l'utilisateur A ne voit pas les projets de B.

## ÉTAPE 5 — Finir l'UI §42 (tout ce qui reste statique)
1. **ADR réels** : route `GET /decisions` sur le Decision Ledger (monté au Lot 1) → panneau Décisions branché + bouton « pourquoi cette décision ».
2. **Panneau Memory** : mémoire projet réelle (ProjectMemory existante) exposée en `GET /memory`.
3. **DNA/Tokens réels dans le panneau Design** (déjà extraits — Lot 3) à la place du JSON en dur restant.
4. **Purger les derniers factices** : modale Design Harmony (gains « +100 % » en dur → vrais scores du Critic), `simulateDokployDeploy` → supprimé (remplacé par un état « déploiement : non disponible » honnête).

## ÉTAPE 6 — Fichiers réels : Explorer CRUD + terminal disque + révisions auto
Le lot le plus risqué volontairement en dernier des fondations :
1. Matérialiser les fichiers projets sur disque (sandbox `workspace/<projectId>/`, feature flag) → le terminal exécute réellement `git status`, `pnpm test` (whitelist inchangée).
2. Explorer : créer/renommer/supprimer/déplacer (les routes backend existent déjà, l'UI les branche).
3. Révision automatique après chaque génération (rollback déjà branché).

## ÉTAPE 7 — Self-Repair branché (§26 CDC)
Le Repair Orchestrator (existe, max 3 cycles, testé) connecté au Quality Gate : findings critiques → plan de réparation → patches appliqués via le MutationOrchestrator → re-critique → gate. Borné et audité (tentatives enregistrées).

## ÉTAPE 8 — Design Intelligence V8 (la différenciation, en 4 sous-lots)
1. Design Direction/Tokens/Rules exposés en API (le token-inferer existe) + écran Studio.
2. AQS + DQI (harmonie + esthétique, déterministes) dans le Quality Gate existant.
3. Boucle d'auto-amélioration bornée : RENDER→CRITIQUE→SCORE→PLAN→MODIFY→RE-RENDER→COMPARE (limites : itérations, tokens, seuil d'amélioration).
4. Régression visuelle multi-viewports 375/768/1024/1440/1920.

## ÉTAPE 9 — Documentation
README d'installation · consolidation SPEC-PHASE + security-audit sous `docs/` · ADR-001… du projet lui-même (Annexe L).

## Garde-fous transverses
- Chaque étape = commits séparés, suite **1067+ verte**, `tsc --noEmit` propre, jamais de push (pas de remote).
- Étapes 3-4 réversibles : interfaces inchangées, fallback JSON/clé-admin conservé pendant la transition.
- Pas de nouvelle dépendance npm à l'étape 3 (node:sqlite intégré) ; aucune dépendance côté front.
- Parallèle utilisateur : rotation de la clé Mistral dès que vous avez la nouvelle (2 min, je l'intègre quand vous voulez).
- Hors périmètre de cette série : billing, WebSocket, i18n, déploiement réel — Phase 4-5 du CDC, décideront plus tard.
