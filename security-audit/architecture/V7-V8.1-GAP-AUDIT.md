## 1. Executive Summary

L'audit architectural approfondi de **Volaco Core** a été mené sous la règle absolue d'intégrité : **aucune ligne de code source n'a été modifiée**, aucun refactoring ni suppression n'a été opéré. L'ensemble des 33 sous-domaines a été inspecté à partir du code réel, des imports, des mécanismes d'exécution, des routes HTTP et des fichiers du Studio frontend.

### Constats Majeurs :
1. **Une infrastructure de sécurité et d'observabilité exemplaire :** La baseline de sécurité est scellée (**SECURITY BASELINE FROZEN**). Les mécanismes d'authentification HMAC-SHA256, isolation multi-locataires (`${tenantId}:${id}`), RBAC 4 rôles avec immunité prototype pollution, audit trail cryptographique SHA-256, rate limiting LRU borné, et protection anti-SSRF asynchrone (DNS lookup A/AAAA, blocage IPv6/IPv4 privées/cloud metadata, redirection interdite) sont opérationnels à 100%.
2. **Une richesse algorithmique pure exceptionnelle dans `packages/core/src/ai-native/` :** 17 modules TypeScript stricts couvrent le DAG d'agents (`agent-runtime`), le state-machine de conversation (`conversation-compass` à 11 états), l'analyse d'impact de graphe (`impact-intelligence`), le graphe sémantique (`semantic-graph`), le DOM normalisé (`visual-intelligence`), l'analyse d'harmonie multi-pages (`design-harmony`), et l'optimisation d'évolution produit (`evolution`). Ces modules totalisent plus de 1670 tests unitaires et d'intégration au vert.
3. **Le grand fossé d'intégration (The Architectural Disconnect) :**
   - **Le Studio (`apps/studio/index.html` — 12 881 lignes) est un monolithe client presque entièrement déconnecté du backend.** Lorsqu'un utilisateur tape un prompt de création ou de modification, le Studio n'interroge ni l'orchestrateur d'agents ni le graphe sémantique. Il envoie un appel direct à `/api/v1/ai/chat/completions` (relais direct LLM) ou se replie sur des templates statiques.
   - **Cinq routes d'intelligence avancée sont câblées dans l'API REST** (`/audit`, `/features`, `/feedback`, `/strategy`, `/evolution`), mais **les moteurs centraux d'exécution de code et d'orchestration (`conversation-intelligence`, `agent-runtime`, `ai-orchestrator`, `mutation-orchestrator`, `visual-intelligence`) ne sont exposés sur AUCUNE route API** (`apps/api/src/routes/`). Ils vivent sous forme de bibliothèques internes testées en mémoire mais jamais instanciées au runtime HTTP.
4. **Persistance en mémoire volatile :** Les projets, révisions et fichiers sur le serveur sont stockés dans des `Map` in-memory. Si le serveur redémarre, le projet par défaut disparaît de la mémoire du serveur, forçant le Studio à vivre en autarcie dans le `localStorage` du navigateur.
5. **Absence d'un `ApplicationModel` unifié :** Il existe trois modèles partiels concurrents : `ApplicationRevision` (dans `model/revision.ts`), `ApplicationDNA` (dans `dna/types.ts`), et `ApplicationSemanticModel` (dans `application-understanding/types.ts`). Ils ne partagent aucun conteneur canonique persistant.

## 33. Architecture Coherence Audit : Doublons et Fractures

Le point critique de l'audit révèle trois fractures architecturales majeures :

1. **Fracture de Persistance (Dual Store Problem) :**
   - Le Studio stocke les applications créées dans le `localStorage` du navigateur sous la clé `vibecode_user_projects`.
   - Le serveur API stocke les projets dans `InMemoryProjectRepository` et les fichiers dans `InMemoryFileStore`.
   - **Conséquence :** Si un utilisateur recharge sa page après un redémarrage du serveur, ses fichiers sont dans le navigateur mais le serveur renvoie HTTP 404 sur les routes `/files`, `/revisions` et `/audit`.
2. **Fracture d'Orchestration IA :**
   - Le Studio appelle directement `/api/v1/ai/chat/completions` avec un prompt monolithique demandant à Codestral de générer un fichier HTML unique.
   - Les moteurs multi-agents `AgentRuntimeService`, `ConversationIntelligenceService` et `MutationOrchestratorService` sont complètement contournés.
3. **Multiplicité des Modèles Applicatifs :**
   - `ApplicationRevision` gère des fichiers bruts avec hashes SHA-256.
   - `ApplicationDNA` analyse l'architecture et les dépendances AST.
   - `ApplicationSemanticModel` extrait les entités métiers, workflows et parcours.
   - **Ces trois représentations ne convergent pas dans une entité racine `ApplicationModel`.**

## 40. Next 10 Implementation Lots (Ordre Optimal)

### **LOT 01 — Unified Storage & Project State Persistence**
- **Objectif :** Rendre la persistance serveur durable sur disque et synchroniser automatiquement avec le Studio.
- **Périmètre :** Adapter `ProjectStore` et `FileStore` pour écrire dans `.volaco_data/` sans casser les interfaces en mémoire.
- **Dépendances :** Aucune.
- **Fichiers :** `packages/core/src/identity/project.ts`, `packages/core/src/file-explorer/store.ts`.
- **Critères d'acceptation :** Un redémarrage du serveur conserve intacts le projet et ses fichiers ; le Studio charge le projet distant sans 404.
- **Risque :** Faible.

### **LOT 02 — Elimination of Legacy Regex Simulators**
- **Objectif :** Supprimer définitivement `createUniversalApp` et `applyIncrementalModification`.
- **Périmètre :** Nettoyage du code mort dans le Studio ; gestion explicite des états d'erreur réseau/LLM.
- **Dépendances :** Lot 01.
- **Fichiers :** `apps/studio/index.html`.
- **Critères d'acceptation :** 0 template statique injecté à l'insu de l'utilisateur ; comportement honnête et transparent.
- **Risque :** Faible.

- **Périmètre :** Création du contrat canonique et du service d'accès centralisé.
- **Dépendances :** Lot 01.
- **Fichiers :** `packages/core/src/model/application-model.ts`, `packages/core/src/model/index.ts`.
- **Critères d'acceptation :** Une entité unique représente l'état complet du projet.
